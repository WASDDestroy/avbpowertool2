# Internationalization (i18n)

How localized strings work in AVBPowerTool2 and how to add new ones.

## How It Works

AVBPowerTool2 uses Python's standard `gettext` machinery, wrapped by a small helper module: `avbpowertool/presentation/i18n.py`.

The design choices that matter:

- **msgids are stable dotted keys, not English sentences.** Every translatable string has an identifier like `read_image_info.title`. The English `.po` file maps that key to its English text; other languages map the same key to their text.
- **The English `.po` file is the source of truth.** `avbpowertool/locale/en/LC_MESSAGES/avbpowertool.po` must contain an entry for every key, even though English is also the fallback. Coverage checks (`check_l10n`) compare other languages against it.
- **`.mo` files are build artifacts.** They are gitignored. `init_i18n` auto-compiles `.po -> .mo` on startup whenever the `.mo` is missing or older than the `.po`.
- **Translations happen only in the presentation layer.** Domain and application code return plain data; only CLI/TUI code calls `_()`.

## File Layout

```
avbpowertool/locale/
  en/LC_MESSAGES/
    avbpowertool.po    <- source of truth (committed)
    avbpowertool.mo    <- compiled (gitignored, auto-generated)
  zh/LC_MESSAGES/
    avbpowertool.po
    avbpowertool.mo
```

The active language is persisted in `settings.json` (`language` setting, default `en`). `bootstrap.py` reads it at startup and calls `init_i18n(language)`, which loads the matching translation catalog with fallback to English. Users switch languages in the TUI via **Settings > Edit settings > Language**; the new language takes effect on the next launch.

## Adding a New String

### Step 1: Pick a key

Use a dotted, feature-scoped key. Conventions:

| Pattern | Used for | Example |
|---|---|---|
| `node.<route>.name` / `node.<route>.description` | Navigation titles/descriptions (`resources/navigation.json` references them) | `node.read_image_info.name` |
| `<feature>.title` | Screen title of a TUI view | `read_image_info.title` |
| `<feature>.<what>` | Messages, prompts, errors within a feature | `read_image_info.no_images` |
| `<feature>.field.<name>` | Formatted output lines | `read_image_info.field.path` |
| `settings.*` | Settings screens (shared across features) | `settings.saved` |

Keys never change once released — views, navigation.json, and translations all reference them.

### Step 2: Add the entry to the English `.po`

`avbpowertool/locale/en/LC_MESSAGES/avbpowertool.po`:

```po
# Read Image Info
msgid "read_image_info.results_title"
msgstr "Image Info Results"
```

Blank line between entries; a `# comment` line above each entry groups strings by feature (the file is organized by feature sections — follow the existing grouping).

### Step 3: Add the entry to every other language `.po`

Same msgid, translated msgstr — e.g. `avbpowertool/locale/zh/LC_MESSAGES/avbpowertool.po`:

```po
msgid "read_image_info.results_title"
msgstr "镜像信息结果"
```

If you skip a language, the fallback logic in `_()` shows the msgid itself (the dotted key) for that language — always fill in all language files. The `Check translations` action (Settings > Check translations, or `check_l10n()`) reports exactly which keys a language is missing.

### Step 4: Call it from presentation code

```python
from avbpowertool.presentation.i18n import _

# plain string
message_screen(stdscr_c, _("read_image_info.title"), lines)

# formatted string: the msgstr may contain {placeholder} fields
lines.append(_("read_image_info.field.path", value=img.image_path))
```

`_()` accepts `str.format()` keyword arguments, so a msgstr like `"  Path: {value}"` is filled in at call time. Unknown/missing placeholders are left as-is rather than raising.

### Step 5: Run

`.mo` files are recompiled automatically the next time the app starts (based on file mtime). If the change doesn't seem to appear, delete the stale `.mo` next to the `.po` and restart.

## Placeholders and Formatting

- Put placeholders in the **msgstr**, not the msgid: msgid is the key (`read_image_info.field.path`), msgstr is the text (`"  Path: {value}"`).
- Use named placeholders (`{value}`, `{count}`) and pass them as kwargs to `_()`.
- Word order differs across languages; named placeholders let translators reorder. Example from the codebase: `_("settings.saved", key=..., old=..., new=...)`.

## Rules and Limitations

The `.po -> .mo` compiler in `i18n.py` is intentionally minimal. Within those limits:

- **No plural forms** (`msgid_plural`/`msgstr[n]`) and **no message contexts** (`msgctxt`). Phrase strings so they don't need plurals, or handle counts outside the translated text.
- **Multiline entries** are supported only as consecutive quoted continuation lines; avoid embedded `\n` beyond simple cases — prefer one msgid per line of output.
- **Never call `_()` in `domain/` or `application/`.** Those layers must stay locale-independent; translate when rendering.
- **Never hardcode user-visible strings in TUI/CLI code** — route them through the catalog so coverage checks can track them. (A handful of legacy raw-string msgids like `_("Exit")` / `_("Back")` exist in `app.py`; new code must use dotted keys.)
- The msgid is what users see if a translation is missing — another reason keys should be descriptive.

## Checking Translation Coverage

Two equivalent ways:

- **TUI:** Settings > Check translations — lists keys present in English but missing in the active language, with the English default text.
- **API:** `check_l10n(language)` returns `{msgid: english_default}` for missing entries.

## Adding a New Language

1. Create `avbpowertool/locale/<code>/LC_MESSAGES/avbpowertool.po` with the standard header:

   ```po
   msgid ""
   msgstr ""
   "Content-Type: text/plain; charset=UTF-8\n"
   "Language: <code>\n"
   ```

2. Translate all msgids (copy the structure from `zh/LC_MESSAGES/avbpowertool.po`; it currently mirrors the English file entry-for-entry). An empty/missing file is tolerated — every string falls back to the msgid — but ship complete files.
3. Register the language as a choice in `SETTING_DEFS` in `avbpowertool/infrastructure/persistence/settings_repository.py`:

   ```python
   "language": {
       "type": "choice",
       "label_key": "settings.language",
       "options": {
           "en": "settings.option.language.en",
           "zh": "settings.option.language.zh",
           "<code>": "settings.option.language.<code>",  # add
       },
       "default": "en",
   },
   ```

4. Add the corresponding `settings.option.language.<code>` entries to all `.po` files.
5. No build step is needed — `init_i18n` compiles the `.mo` on first run.

## Testing

- `tests/integration/test_bootstrap_i18n.py` covers language resolution: persisted setting applied, explicit override wins, missing settings default to `en`.
- When adding strings to a view with existing tests, keep the tests asserting against msgids (e.g. `read_image_info.title`), not translated text — tests run with the default catalog and must not depend on translations.
